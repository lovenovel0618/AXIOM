# 53｜工程治理與開發者工作流

> AXIOM v2.9 設計規格｜文件 ID AX-53｜狀態：待實作、待驗收｜2026-10-20

## 本章定位

本章把「規格」與「可執行工程」之間的接口固定下來：三類機器可讀登錄的單一真實來源、未啟用能力的閘門與投影規則、倉庫目錄骨架與 WBS 對應，以及開發者在提交前必須通過的品質閘門。本章只描述規格，所有案例與產品狀態維持 NOT_RUN。

從零開工的順序、各階段交付與驗收、第一輪工作票及交接模板見 [AX-31 開發流程與步驟](<../11-交付/31-工作拆解WBS與依賴.md#依企劃案落地的開發流程>)；本章定義每一步須遵守的工程規則。

## 三類登錄的單一真實來源

錯誤碼、能力與政策過去只散落在各章散文，實作與前端容易各自解讀。以下三份登錄為唯一真實來源（SSOT）；散文與 OpenAPI 由工具雙向校驗，不得只改其中一處。

| 登錄檔 | 權威章 | 內容 | 拒絕行為 |
|---|---|---|---|
| error-codes-v1.json | AX-21 | 穩定錯誤碼、scope、HTTP 狀態、retryable | 未登錄碼不得出現在 OpenAPI 或回應 |
| capability-registry-v1.json | AX-30 | 能力、啟用里程碑、保留端點 | 未達里程碑回 FEATURE_DISABLED |
| policy-registry-v1.json | AX-26 | 發布／釋出／模型路由政策與決策閘門 | 決策未關閉一律 BLOCKED |

契約檔位於 docs/企劃案/contracts。錯誤碼登錄以 AX-21 兩種結構化來源為準：錯誤表登錄 scope 為 HTTP 的穩定碼，worker 清單登錄 scope 為 WORKER 的內部碼，兩者聯集即登錄的穩定碼全集，且同一碼不跨兩處。OpenAPI 的 Error.code 枚舉必須等於登錄中 http_exposed 為真者；未登錄碼一律拒絕，不能以自由字串放行。錯誤碼與能力、政策的交叉引用如下。

- 錯誤碼 SSOT：[error-codes-v1.json](<../contracts/error-codes-v1.json>)，權威為 [AX-21](<../07-資料與API/21-API與任務契約.md>)，錯誤 envelope 欄位固定為 code、message、details、request_id、retryable。登錄規則：scope 為 HTTP 的穩定碼必附權威狀態；scope 為 WORKER 的碼不固定 HTTP 狀態，即使如 FEATURE_DISABLED 會被投影到 HTTP 邊界（能力／政策停用），其 http_exposed 仍為真而 http_status 為 null。
- 能力 SSOT：[capability-registry-v1.json](<../contracts/capability-registry-v1.json>)，權威為 [AX-30](<../11-交付/30-里程碑與分階段開發計畫.md>)。
- 政策 SSOT：[policy-registry-v1.json](<../contracts/policy-registry-v1.json>)，權威為 [AX-26](<../09-非功能/26-安全隱私與可信執行.md>)，決策閘門為 D-05。

## 能力閘門與投影規則

能力以 AX-30 的里程碑為唯一依據。未達 enabled_from 時，服務與介面必須回 FEATURE_DISABLED，且不得把未啟用端點寫進 OpenAPI 或在前端先行開關；API 與 UI 只能由同一份 capability-registry-v1.json 投影，禁止各自硬編碼。實作能力清單如下。

- EXPERIENCE_MEMORY：經驗記憶與檢索，M4 起，保留端點 /experiences。
- MODEL_ROUTING：AI 模型路由與資料外送，M4 起，保留端點 /models。
- FORMAL_PROOF：符號推導與形式化證明，M5 起，保留端點 /proofs。
- DUAL_SEQUENCE：雙序列研究，M6 起。
- MULTI_SEQUENCE：多維多序列研究，M7 起。
- STRATEGY_TRAINING：策略學習與微調，M7 起。

以目前基線 M3 為界，M4 以後的保留端點不得出現在 OpenAPI；啟用時必須同時提出對應契約、遷移與 gate，不能靠既有 enum 或選單宣告能力已可用。

## 政策登錄與 Fail-Closed

發布、摘要釋出與模型路由政策在 D-05 關閉前一律 BLOCKED。核准後才由具名負責人填入 decision、evidence_uri、approved_by 與 approved_at，文件維護者不得代簽。政策登錄內容如下。

- PUBLICATION_POLICY：發布政策，授權欄位 publication_policy_artifact_id，未核准回 PUBLICATION_POLICY_BLOCKED。
- DISCLOSURE_POLICY：摘要釋出政策，授權欄位 disclosure policy，未核准回 DISCLOSURE_POLICY_BLOCKED。
- MODEL_ROUTING_POLICY：模型路由與資料外送政策，授權欄位 policy_version，未核准回 FEATURE_DISABLED。

政策缺失時以 BLOCKED 驗收，不因一般 reviewer 按核准便放行；模型失效只能在同等或更嚴格政策的本地路由間回退。

## 倉庫目錄骨架

下列骨架為待實作規格，與 WBS 對應；尚未建立任何目錄或服務。跨層變更必須同時落 DB 約束、API／payload、UI 投影、權限與測試。

| 目錄 | 用途 | 對應 WBS |
|---|---|---|
| backend/ | Django／DRF 服務、Celery worker 與領域模組 | 02、06、07、08、09、10、11、12、15 |
| frontend/ | Vue 3 工作台與可視化 | 14 |
| contracts/ | 機器可讀契約與 fixture（源於 docs/企劃案/contracts） | 02、03 |
| infra/ | Compose、遷移 job、healthcheck 與 smoke | 15、16 |
| docs/企劃案/ | 本規格集與文件檢查工具 | 01 |
| tests/ | 單元、整合、契約與 E2E | 各 WBS 驗收 |

目錄與命名為規格提案：新增模組需落在上表範圍並在 AX-31 對應 WBS，超出範圍者先更新本章與 AX-31。

## 開發者工作流與完成定義

分支、提交與審查遵循下列常規，避免版本與追溯脫節。

| 面向 | 規則 |
|---|---|
| 分支 | 主幹 master；功能分支自 master 切出，命名 feature／fix／docs 前綴 |
| 提交 | 一個提交一件事；訊息說明動機與影響契約，不夾帶無關格式化 |
| 變更程序 | 先改權威文件與 schema，再更新引用章、fixture、追溯表與索引（依 AX-48） |
| PR／DoD | 需求對照、介面契約、測試證據、效能測量、風險與文件更新缺一不可 |
| 品質閘 | py_compile、pyright 嚴格模式、check_docs.py 與契約檢查全過，必要時補 E2E |

文件與產品驗收嚴格分離：文件／fixture 檢查通過不等同產品測試通過，未執行案例一律 NOT_RUN。

## 品質閘門指令

於倉庫根目錄以 Python 3.14 建立本地環境後執行；任一關卡失敗即不交付。

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r docs/企劃案/tools/requirements-dev.txt
.venv/bin/pyright
.venv/bin/python docs/企劃案/tools/check_docs.py
.venv/bin/python docs/企劃案/tools/check_docs.py --write-manifest
.venv/bin/python docs/企劃案/tools/check_docs.py
```

`check_docs.py` 額外雙向校驗錯誤碼 SSOT 與 AX-21 散文、OpenAPI 枚舉，能力登錄與里程碑／OpenAPI，以及政策登錄與 D-05；CI 的 docs-check 工作流在 push 與 PR 執行同一組檢查。

以下為預定測試，狀態皆 NOT_RUN；實際證據依 AX-46 登錄。
