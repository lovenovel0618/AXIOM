# 08｜部署與運算資源規劃

> AXIOM v2.1 整合基線｜文件 ID AX-08｜狀態：設計基線（未實作）｜2026-10-19

## 1. 文件定位與決策摘要

資源分池與排程：interactive < short_cpu < batch_cpu/gpu；GPU 工作需顯式宣告 VRAM；公式搜尋優先分段 checkpoint；單研究設定最大並行度，避免一個租戶吃滿所有資源。

**設計原則**：每個規範都要能轉換成可測試的行為、可追溯的證據或明確的工程決策；凡屬目標數字均非已實測結果。

## 2. 章節專屬規格

### 環境分層

Local Docker Compose（macOS 開發／Windows WSL2 架設）：Django、Vue、PostgreSQL、Redis、MinIO、Ollama 選配；CI：隔離基準與安全掃描；Staging：性能與故障演練；Production：獨立資料與工作池。

### 本地容器化（開發與架設）

同一份 Docker Compose 定義橫跨兩個平台：**開發**於 macOS，**架設**於 Windows 11 + WSL2。服務清單、資料卷、環境變數、健康檢查、平台注意事項與跨環境一致性見 [41-Docker本地架設指南](<../03-架構/41-Docker本地架設指南.md>)。原則：

- 容器映像與組態可重建，Redis 與容器本機狀態不作為唯一永久資料來源。
- 依賴以健康檢查表達，不以固定等待時間取代；必要服務不健康時不提供服務。
- proof／sandbox worker 於兩環境皆維持無外網、唯讀檔案系統與非 root 執行。
- macOS 無 GPU 直通，gpu 佇列不啟用；WSL2 是否可用 GPU 直通待確認，確認前一律視為不可用並走 CPU。
- 兩環境共用 `.env` 鍵集合與映像標籤，差異僅以覆寫檔表達，確保基準數據可互相比較。

### 工作池

light：資料清理／特徵；search：CPU 符號迴歸；precision：mpmath 高精度；gpu：本地模型推理；proof：受限形式化驗證。各佇列獨立配額、超時、併發、記憶體上限。

### 容量方法

先測單次工作 CPU 秒、記憶體峰值、候選數、資料量與 I/O；按到達率與 P95 服務時間估算併發，再壓測。避免未實測就宣稱固定硬體規格足夠。

### 復原

每日一致性備份與物件版本化；定期恢復演練；RPO/RTO 由產品等級決定；長任務以 checkpoint 減少重跑。

## 3. 能力分解與詳細規格

### 3.1 分層與部署原則

Vue SPA 與 Django API 分離；研究編排器負責任務與策略；Python 計算工作池執行搜尋；隔離證明服務與 LLM gateway；PostgreSQL 保存權威資料，MinIO 保存大物件。

**強制規則／例外處理**：LLM 不可直接操作資料庫或宿主作業系統；長時間計算不得阻塞 HTTP worker。

### 3.2 計算工作池

分 CPU 短任務、CPU 重任務、GPU 任務、符號證明任務；依計算預算、資料敏感等級及演算法需求派送。

**強制規則／例外處理**：排程器必須提供優先級、超時、取消、重試、租約、檢查點與重複任務去重。

### 3.3 版本與依賴

服務 API、公式 DSL、資料 schema、事件 schema、演算法插件與模型權重各自版本化；跨服務契約採向後相容與遷移窗口。

**強制規則／例外處理**：升級時使用契約測試、影子流量與回滾程序。

### 3.4 擴充與隔離

研究租戶、資料空間、權限與配額隔離；外部 AI 模型透過統一 Gateway；數學運算只能在安全執行器內。

**強制規則／例外處理**：高風險輸入、模型生成內容和上傳檔案均視為不可信。

## 4. 執行規範與設計檢查點

1. **前置檢查**：啟動「部署與運算資源規劃」相關功能前，驗證資料版本、權限、依賴服務、研究模式及資源配額。

2. **核心處理**：依本文件第 2、3 節執行，記錄所有關鍵決策、失敗原因、所採用的假設及每一個中間產物的來源。

3. **完成條件**：輸出不僅有成功結果，也有失敗、部分成功、歧義及不可執行狀態；不得默默回退成看似正常的結果。

4. **品質檢查**：用正常、邊界、異常、對抗、重試、並行與取消情境驗證行為；保留對照測試與審核記錄。

## 6. 失敗情境與降級策略

| 失敗或風險 | 系統反應 | 留存證據 |
|---|---|---|
| 輸入不符合「部署與運算資源規劃」要求 | 拒絕執行並提供可修正的欄位錯誤 | 輸入版本、驗證規則、錯誤代碼 |
| 依賴服務中斷或超時 | 有限次重試；超出預算即終止並保存 checkpoint | 服務版本、耗時、重試紀錄 |
| 結果彼此衝突或證據不足 | 保留候選及歧義，不提升證據等級 | 候選集合、反例、驗證集 |
| 資源配額超出 | 中止重運算，保留已完成的可信部分結果 | CPU/GPU 秒、記憶體峰值、任務狀態 |

## 7. 可執行驗收案例

**AC-08-01 正常路徑**：給定完整合法的輸入、固定資料版本與計算預算，執行「部署與運算資源規劃」流程，必須產出可追溯的結果與完成狀態。

**AC-08-02 異常路徑**：故意提供缺欄、錯誤型別、超時或不合法狀態，必須得到明確診斷且不得產生已驗證的假結果。

**AC-08-03 重現性**：在固定輸入、版本、隨機種子與執行環境下重跑，輸出應符合預先定義的決定性或容差標準。

**AC-08-04 權限與審核**：未授權角色不得讀取或發布研究資料；審核者能查詢完整證據鏈。

## 整合後的佇列命名

`interactive`、`short_cpu`、`batch_cpu` 表達排程等級；Compose 中的實體佇列沿用既有名稱，避免兩套文件被誤解為兩套部署。

| 排程等級／能力 | 實體佇列 | 工作與限制 |
|---|---|---|
| short_cpu | light | 語意檢查、清理、特徵，受互動延遲預算約束 |
| batch_cpu | search | 公式搜尋，定期 checkpoint |
| 高精度 CPU | precision | 依精度與記憶體限制隔離 |
| GPU | gpu | 僅宿主能力確認後啟用；明確宣告 VRAM |
| 證明／不可信求值 | proof | 受限執行，不能取得資料庫憑證 |

interactive 請求由 HTTP 層受理；長任務仍提交工作池。每一佇列分開記錄並發、租約、逾時與總預算。開發與架設平台維持 ADR-006；後續正式叢集部署才是待決事項。
