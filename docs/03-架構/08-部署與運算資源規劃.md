# 08｜部署與運算資源規劃

> AXIOM v2.4 設計規格｜文件 ID AX-08｜狀態：待實作、待驗收｜2026-10-20

## 文件定位與決策摘要

資源分池與排程：interactive < short_cpu < batch_cpu/gpu；GPU 工作需顯式宣告 VRAM；公式搜尋優先分段 checkpoint；單研究設定最大並行度，避免一個租戶吃滿所有資源。

## 章節專屬規格

### 環境分層

Local Docker Compose（macOS 開發／Windows WSL2 架設）：Django、Vue、PostgreSQL、Redis、MinIO、Ollama 選配；CI：隔離基準與安全掃描；Staging：性能與故障演練；Production：獨立資料與工作池。

### 本地容器化（開發與架設）

同一份 Docker Compose 定義橫跨兩個平台：**開發**於 macOS，**架設**於 Windows 11 + WSL2。服務清單、資料卷、環境變數、健康檢查、平台注意事項與跨環境一致性見 [41-Docker本地架設指南](<../03-架構/41-Docker本地架設指南.md>)。原則：

- 容器映像與組態可重建，Redis 與容器本機狀態不作為唯一永久資料來源。
- 依賴以健康檢查表達，不以固定等待時間取代；必要服務不健康時不提供服務。
- proof／sandbox worker 於兩環境皆維持無外網、唯讀檔案系統與非 root 執行。
- macOS 無 GPU 直通，gpu 佇列不啟用；WSL2 是否可用 GPU 直通待確認，確認前一律視為不可用並走 CPU。
- 兩環境共用 `.env` 鍵集合與映像標籤，差異僅以覆寫檔表達，確保基準數據可互相比較。

### 工作池

light：資料清理／特徵；search：CPU 符號迴歸；precision：mpmath 高精度；gpu：本地模型推理；proof：受限形式化驗證。各佇列獨立配額、超時、併發、記憶體上限。

### 容量方法

先測單次工作 CPU 秒、記憶體峰值、候選數、資料量與 I/O；按到達率與 P95 服務時間估算併發，再壓測。避免未實測就宣稱固定硬體規格足夠。

### 復原

每日一致性備份與物件版本化；定期恢復演練；RPO/RTO 由產品等級決定；長任務以 checkpoint 減少重跑。

## 整合後的佇列命名

`interactive`、`short_cpu`、`batch_cpu` 表達排程等級；Compose 中的實體佇列沿用既有名稱，避免兩套文件被誤解為兩套部署。

| 排程等級／能力 | 實體佇列 | 工作與限制 |
|---|---|---|
| short_cpu | light | 語意檢查、清理、特徵，受互動延遲預算約束 |
| batch_cpu | search | 公式搜尋，定期 checkpoint |
| 高精度 CPU | precision | 依精度與記憶體限制隔離 |
| GPU | gpu | 僅宿主能力確認後啟用；明確宣告 VRAM |
| 證明／不可信求值 | proof | 受限執行，不能取得資料庫憑證 |

interactive 請求由 HTTP 層受理；長任務仍提交工作池。每一佇列分開記錄並發、租約、逾時與總預算。開發與架設平台維持 ADR-006；後續正式叢集部署才是待決事項。
