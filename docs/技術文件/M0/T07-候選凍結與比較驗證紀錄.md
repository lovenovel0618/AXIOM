# T07｜候選凍結與比較驗證紀錄

日期：2026-10-22；owner／SELF_REVIEW：project-owner；承接 77b4d2e。切片設計見[技術設計](<T07-候選凍結與比較設計.md>)。本批把 #3 的離線擬合結果落成權威的候選、擬合與凍結身分，並補上 ObservationSplit 與 RepresentationSpec 的最小不可變 recipe；T07 仍 IN_PROGRESS。

## 交付範圍

依 AX-47 新增五張 catalog 表：`Candidate`、`FitRun`、`FrozenCandidate`、`ObservationSplit`、`RepresentationSpec`。服務層依職責分檔為 `catalog/candidates.py`（候選、擬合與兩個 recipe 落庫）與 `catalog/freezing.py`（凍結與比較決策）；runtime 端新增 `catalog/search_run.py` 承載最小權威 run 列，並擴充既有 run guard 允許 `SEARCH`／`FIT`。

本批的 run 是「最小權威列承載」：`SEARCH` 與 `FIT` 的 root run 建為 `RuntimeRun`（`control_only=False`），狀態停在 `QUEUED`，不派 worker、不建 attempt、不建 InputSnapshot、不建 RootBudget／Reservation、不建任何帳本列；`catalog/tasks.py` 既有兩個 relay 只掃 `INGEST` 與 `ProfileBinding`，故這些列不會被任何 relay 撿走。`budget_account_id`／`input_artifact_id`／`execution_manifest_id` 為 schema 必填的身分欄位，本批刻意保留為未落庫的 UUID，代表「沒有預留、沒有固定輸入、沒有可派送 manifest」，而不是宣稱它們存在。

`Candidate.search_run`、`FitRun.run`、`FrozenCandidate` 精確引用單一 FitRun；`Candidate unique(search_run_id, equation_version_id)`、`FitRun unique(run_id)`、`FrozenCandidate unique(candidate_id, fit_run_id)`、`ObservationSplit unique(dataset_version_id, row_ids_hash)`，五表皆補 `(id, tenant)` 唯一鍵供複合外鍵引用。離線順序沿用 #3 的決定性 tie-break，並把名次持久化為 `development_rank`（1 起算）。

凍結鏈以 `contract_scenarios` 的 `freeze_decision` 為權威裁決，逐條實作 `freeze_policy_decision` → `freeze_recipe_decision` → `FIT_REFERENCE_MISMATCH`／`EQUATION_MISMATCH` → `frozen_binding_decision`（`BINDING_MISMATCH`／`PARAMETER_NOT_CANONICAL`／`BINDING_HASH_MISMATCH`）→ `SNAPSHOT_MISMATCH` → `RANK_MISMATCH` → `ACCEPT`，回傳同一組穩定代碼。`SNAPSHOT_MISMATCH` 屬 `FrozenSubmission.snapshot_hash`，本批不建立該物件，故只有 conformance 對照的純函式呼叫會走到該分支，落庫路徑不觸及。`parameter_binding_hash` 以名稱排序、十進位去冗餘零後的 canonical JSON 算 SHA-256，並以範例 `{"a":"2","b":"1"}` 的 `f7a837dc…` 對照。零候選沿用 `empty_search_decision`：`proposed_count` 為零時不建立任何 Candidate，回報 `SUCCEEDED:INSUFFICIENT_EVIDENCE:NO_VALID_CANDIDATE`。

本批同時修正 AX-47 已裁定的落差：`row_ids_hash` 的雜湊輸入改取 `{fit, development, final_test, gap_rows, lookback_rows, horizon_rows}` 六鍵 canonical JSON（原只雜湊三個分區陣列），`catalog/research_validation.py` 與 `ingestion/research.py` 同步，既有測試期望值一併更新。

## SELF_REVIEW

- 實測發現並修正真實缺陷（一）：`catalog_business_guard()` 是掛在 `runtime_runtimerun`、`catalog_ingestbinding`、`catalog_profilebinding` 三表上的共用 trigger function，後兩者沒有 `document` 欄位。PL/pgSQL 對 `NEW.xxx` 的欄位解析在編譯期針對 record 型別進行，**不因 `AND` 左運算元為 false 而短路**，故原寫法在 binding 表上一律拋 `record "new" has no field "document"`；今改用已靜態型別化的區域變數 `r runtime_runtimerun` 讀取（`r.document->>'type'`）修正。
- 實測發現並修正真實缺陷（二）：`runtime-v2.schema.json` 與 0020 guard 都要求 `FitRun` 有 `fit_rows_hash` 欄位（＝fit 列陣列 canonical SHA-256，與 `RepresentationSpec.fit_rows_hash`、`profile.py` 既有規則同值），但 0019 建表時漏了此欄位；今補上欄位、`^[0-9a-f]{64}$` CheckConstraint，並由 `candidates.py` 的 `_fit_run` 帶入。
- 實測發現並修正真實缺陷（三）：`frozen_candidate` 以 `fit.id`（UUID）與 `{str(item) …}`（字串集合）比較永為假，造成合法的凍結被誤判 `FIT_REFERENCE_MISMATCH`；今改為 `str(fit.id)` 比較。
- 凍結採 Fail-Closed：`frozen_candidate` 逐條驗證 recipe、公式、引用與 binding 後才落庫，任一不符即拒絕且不寫入任何列；同 `(candidate_id, fit_run_id)` 重複呼叫讀回同一列，不重建身分。
- `FrozenCandidate.parameters` 是該 FitRun 的完整正規副本，`dsl_identity_hash` 直接取自 EquationVersion，不接受呼叫端另行宣稱；本批不含 `snapshot_hash`。
- 零候選與預算不足只落在服務層回報並帶 `product_status=NOT_RUN`，不寫進 run 的 `stop_reason`，避免以不存在的事件冒充已完成的搜尋。
- 本批不建立 `FrozenSubmission`、不做 `final_test` 評估、不派送任何 run、不開放對外端點；`final_test` 不在任何輸入介面。

## SELF_REVIEW

- Fail-Closed 的核心是「探索階段不得冒充最終評估」：`final_bindings` 以四項交叉核對把 `FINAL_ONLY`＋`FINAL_TEST` 綁成不可分的身分，任何一項放寬都使候選凍結失去意義，故以 `ValueError("FINAL TEST binding mismatch")` 直接拒絕且不寫任何列。
- 起始 `dispatch_stage` 由型別裁決而非呼叫端自選，避免呼叫端以 `SEARCH_OPEN` 挾帶最終評估 manifest 取得探索資源。
- `semantic_profile_hash` 是 `ExecutionManifest` 的 schema 必填欄位，先前建構時漏填；本批補上並由測試鎖定，避免以缺欄 manifest 派送。
- `limit_for` 不以較小的假預留超賣容量：設定限額與剩餘任一不足即拒，維持兩層帳本「唯一扣帳入口」的一致性。
- root 入庫會 `emit("RunQueued")`，但既有 relay 只掃 `INGEST` 與 `ProfileBinding`，故本批仍不宣稱 `final_test` 已執行、也未開放槽位端點。

## 比較語意與實務邊界（#5 續）

日期：2026-10-24；owner／SELF_REVIEW：project-owner；承接 b4f8775。設計補記見[技術設計](<T07-候選凍結與比較設計.md>)的「後續切片：比較語意與實務邊界」節。上節所列「分母與拒答理由的完整語意（paired bootstrap、practical margin、`AMBIGUOUS`）」於本節收束；T07 仍 IN_PROGRESS，產品 Gate 仍 NOT_RUN。

### 交付範圍

`mathematics/comparison.py` 是比較語意的純計算核心：`scale(iqr, resolution, override)` 取 `max(IQR, 解析度)`，兩者皆零時僅認預先註冊的正覆寫值；`bound(scale, ratio)` 得實務外邊界；`baseline_losses(prediction, targets)` 產生固定預測對每個 final 目標的逐列損失；`interval(candidate, baseline, seed, replicates)` 對配對差做 IID 有放回重抽樣並取 95% 百分位區間；`classify(lower, upper, margin)` 產出 `SUPPORTED`／`AMBIGUOUS`／`INSUFFICIENT_EVIDENCE`／`FALSIFIED` 四態。

`interval()` 的重抽樣索引由 `identity_hash(["axiom-paired-bootstrap-sha256-v1", seed, replicate, draw]) % count` 導出，不依賴直譯器 PRNG，故同一政策與同一批列跨環境、跨 Python 版本可重現；`quantile` 沿用 `mathematics/metrics.py` 既有實作。`mathematics/metrics.py` 新增 `residuals()` 回傳 matched 的 `(target, loss)`，`score()` 與配對來源共用，確保計數、`mae`／`rmse` 與配對一致。

`catalog/final_evaluator.py` 以 `_fit_summary`（`ResearchState.quality_id` → `QualityReport.fit_summary`）、`_decimal`、`_baseline`、`_margin`、`_outcome` 接線；`_outcome` 先驗 `error_model`／`comparison_method`／分母／baseline／margin，通過後才以 lambda 延遲呼叫 `residuals` 取配對差並分類，故所有拒答分支都不觸發重抽樣。
