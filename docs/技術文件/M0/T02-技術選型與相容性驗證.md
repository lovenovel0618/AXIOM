# M0／T02｜技術選型與相容性驗證

本文件先於對應驗證程式建立。依 [AX-31](<../../企劃案/11-交付/31-工作拆解WBS與依賴.md>) 的 T02，先驗證最小技術組合，為 T04 工程骨架提供鎖定依賴與重現方式；目前尚未建立產品服務。

## 選型與依據

| 範圍 | 本輪候選 | 原因與權威 |
|---|---|---|
| 產品 Python | CPython 3.13，實測後鎖定 patch | [Django 5.2](https://docs.djangoproject.com/en/5.2/releases/5.2/)與 [DRF 3.16](https://www.django-rest-framework.org/community/3.16-announcement/)明列支援；[Celery 5.6](https://docs.celeryq.dev/en/stable/history/whatsnew-5.6.html)支援此版；不把文件工具 Python 3.14 當成產品已相容 |
| 後端 | Django 5.2 LTS、DRF 3.x、Celery 5.6、Redis client、psycopg 3 | [Django 支援表](https://www.djangoproject.com/download/)為 5.2 提供較長維護期；實際 patch 與間接依賴由鎖檔固定 |
| 數學／匯入 | NumPy 2、SciPy 1、SymPy 1、mpmath 1、Polars 1 | 驗證公開線性資料的數值擬合、符號／數值互通、高精度求值及表格讀取；不是正式盲測或完整 DSL |
| 前端 | Node 24、Vue 3、TypeScript、Vite 8、Pinia、Vue Router | [Node 官方支援週期](https://github.com/nodejs/Release)、[Vite 環境條件](https://vite.dev/guide/)；宿主已有 Node 26，改在隔離 Node 24 容器驗證，不改宿主預設 |
| 資料服務 | PostgreSQL 16、Redis 7，隔離容器 | 對齊 AX-41 既定方向，實測 Django migration／ORM、psycopg 交易與 Celery 經 Redis 的真實非同步工作 |

版本資訊核對日為 2026-10-20；選用維護中的穩定版本，排除 pre-release。AX-41 的 Python 3.12／Node 20 原為待實作示例，T04 需以本輪已驗證基線同步建立實際映像，不直接照抄舊示例。

## 實作前的驗證契約

- 驗證代碼及 lock 位於 `tools/compatibility/`，只用於 T02，不建 backend／frontend 產品目錄，不提供對外 API。
- `requirements.in` 記錄直接依賴範圍；`requirements.lock` 由 uv 產生精確版本與 SHA-256。安裝使用 `--require-hashes`，不改現有 `.venv`；本機另用 `.venv-compat`。
- 前端 `package-lock.json` 固定精確間接依賴，使用 `npm ci`；驗證 mount 前的型別與 production build，以及 Vue SSR／Pinia／Router 最小互通。不把 SSR 測試視為瀏覽器 E2E。
- `python_probe.py` 的第三方模組在隔離產品環境動態載入；工具／測試本身維持 strict 型別，不以停用 import 診斷代替相容性測試。輸出每個 probe 的 PASS／FAIL／NOT_RUN 及版本、平台，任一實際失敗退出 1。
- 本機無資料服務參數時，Django 使用記憶體 SQLite，只驗證 ORM／DRF／數學；PostgreSQL 及 Redis／Celery 網路測試明列 NOT_RUN。容器加 `--require-services` 時，缺少設定或任一服務未測即退出 1，不冒充完整通過。
- 使用專用 Compose project、內部服務網路及短命資料，不公開宿主服務埠，不觸碰其他專案容器／volume。此隔離 harness 只存在於無宿主埠的內部網路，PostgreSQL 以 `POSTGRES_HOST_AUTH_METHOD: trust` 啟動、連線字串不含密碼，因此不保存任何固定憑證；報告不保存連線字串，測試完成移除本 project 容器及 volume。
- Celery 必須啟動真實 worker、透過 Redis 派送並取得結果；不以 eager 模式或 memory broker 冒充。worker 在 finally 停止，外層有時限。
- probe 的隔離資料可刪除；Django contenttypes migration 及 ORM 只在專用測試 DB 執行。不得對真實業務 DB 使用此工具。

## 驗證順序與交付

1. 在 macOS arm64 建 CPython 3.13 獨立環境，解依賴、鎖檔並以 hashes 安裝；執行本機 Python probes。
2. 以 Linux arm64 Python 3.13 容器重新從 lock 安裝，啟動專用 PostgreSQL／Redis，實測 ORM／DRF／交易／Celery 與數學組合。
3. Node 24 容器建立前端 lock、型別檢查、測試及 production build；再次用 npm ci 重現，保存 npm dependency inventory 與授權資料。
4. 保存 Python 環境 inventory／授權 metadata、Node lock／授權 metadata、容器 image digest 與 probe JSON。套件 license metadata 是盤點資料，不等同法律核准；未知授權標記待查，不宣稱通過完整資安／授權 gate。
5. 增加工具失敗分支的單元測試，執行 Pyright strict、Sonar、原有文件／契約驗證、連結與差異檢查，保存 [驗證紀錄](<T02-驗證紀錄.md>)，commit／push。

Linux Docker Desktop 的 arm64 測試不能代表 Windows WSL2／Linux amd64。WSL2 實機保持 NOT_RUN，T04 另交執行證據；CI 可增加 Linux amd64 probe，但未實際看到遠端結果前不標通過。

## 測試案例

| 案例 | 預期 |
|---|---|
| Django migration／ORM 與 DRF 序列化 | 儲存後可查回，JSON 序列化符合預期 |
| psycopg／PostgreSQL | 專用交易可查詢並 rollback，不污染其他 DB |
| Redis／Celery 真實任務 | 透過獨立 worker 回傳精確答案；無服務時 NOT_RUN，嚴格模式失敗 |
| NumPy／SciPy／SymPy／mpmath／Polars | 線性係數及符號導數正確、高精度與列數符合固定輸入 |
| Vue／Pinia／Router／TypeScript／Vite | SSR 固定輸出、路由及 store 測試、型別與 build 通過 |
| 缺依賴、錯誤數值或例外 | probe FAIL、程序退出 1，其他 probe 的結果仍可見 |
| 一般／嚴格模式 | 未執行服務明列；嚴格模式不能忽略 NOT_RUN |

PySR／Julia、PySINDy、pgvector、GPU、外部 LLM、proof、訓練及 UI 圖表套件依未來實際需求另開技術票；MinIO adapter 與物件存取測試在 T04／T05 完成，不把本輪 DB／broker 成功當作物件儲存已驗收。單人自我檢查，不等待其他開發者。

## 重現指令

從倉庫根目錄執行。本機驗證不更換文件工具 `.venv`：

```sh
uv python install 3.13.15 --no-bin
uv venv --python 3.13.15 .venv-compat
uv pip sync --python .venv-compat/bin/python --require-hashes tools/compatibility/requirements.lock
.venv-compat/bin/python -m tools.compatibility.python_probe
```

容器完整驗證使用已固定 digest 的 Python／PostgreSQL／Redis；依序執行，失敗時也要執行最後的清理命令。CI 以 `if: always()` 確保清理：

```sh
docker compose -p axiom-t02-compat -f tools/compatibility/compose.yaml build
docker compose -p axiom-t02-compat -f tools/compatibility/compose.yaml up -d --wait postgres redis
docker compose -p axiom-t02-compat -f tools/compatibility/compose.yaml run --no-deps --rm -T probe
docker compose -p axiom-t02-compat -f tools/compatibility/compose.yaml down --volumes
```

前端在隔離 Node 容器重現；`.node-version` 固定已測的 24.22.0，CI 讀取同一檔案：

```sh
docker run --rm -v "$PWD/tools/compatibility/frontend:/work" -w /work node:24@sha256:14078204b6bb268c107ceff6d3c43f45a888105e5c2b18b14c32b3409d93a1b0 sh -c 'npm ci --ignore-scripts && npm run typecheck && npm test && npm run build'
```

Python SBOM 以 [CycloneDX Python](https://cyclonedx-bom-tool.readthedocs.io/en/latest/usage.html) 從實際環境產生，工具固定 7.5.0；Node 以實測容器中的 npm 11.19.1 產生，兩者均保留依賴關係：

```sh
uvx --from cyclonedx-bom==7.5.0 cyclonedx-py environment .venv-compat/bin/python --output-reproducible --validate -o /tmp/axiom-python-sbom.json
```

前端容器內執行 `node record.mjs` 取得 lock inventory；`npm sbom --sbom-format=cyclonedx` 取得已安裝依賴的 SBOM。lock inventory 可包含其他架構未安裝的 optional 依賴，與單一平台 SBOM 筆數不同是預期行為。此輪 SBOM 不包含未來產品或整個容器 OS 的所有套件；T04 建產品映像後須另產映像層 SBOM。

## 已測環境與下一步界線

本機 macOS arm64 為 CPython 3.13.15；固定 Linux arm64 映像為 CPython 3.13.16，兩者使用相同依賴 lock。現有 uv 0.12.5 無可下載的 macOS 3.13.16，因此不聲稱本機測過該 patch，也不為此更換全域 uv。後續共用產品容器以已實測的 Linux 3.13.16 為候選；patch 變更仍需重跑。

本輪技術交付涵蓋可重現的候選基線、代碼、實測及依賴盤點。Windows WSL2／amd64、瀏覽器 E2E、正式資安及完整授權核准尚未執行；它們各自記錄待辦，不阻止 T03 的公開 fixture 設計。T01 JSON 是建立時的規劃快照，T02 的實際進度與證據以本技術文件索引及驗證紀錄為準，不以舊快照中的 NOT_STARTED 隱藏本輪實測。
