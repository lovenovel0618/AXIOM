# T07 候選凍結與比較設計

狀態：設計中；T07 仍為 IN_PROGRESS。本批把 #3 的離線擬合結果落成權威的候選、擬合與凍結身分，並補上 ObservationSplit 與 RepresentationSpec 的最小不可變 recipe；不建立 FrozenSubmission、不做 `final_test` 評估、不派送任何 run、不開放對外端點。

## 交付邊界

新增五張 catalog 表與兩個服務模組：`Candidate`、`FitRun`、`FrozenCandidate`、`ObservationSplit`、`RepresentationSpec`，服務層依職責分檔為 `catalog/candidates.py`（候選、擬合與兩個 recipe 的落庫）與 `catalog/freezing.py`（凍結與比較決策）。runtime 端只擴充既有 Run guard 與新增 `catalog/search_run.py`，用來承載最小權威 run 列。

AX-47 的物件責任要求 `Candidate.search_run`、`FitRun.run`、`FrozenCandidate` 精確引用單一 FitRun；AX-43 的唯一鍵表要求 `Candidate unique(search_run_id, equation_version_id)` 與 `FitRun unique(run_id)`。因此本批必須同時提供 run 載體、候選身分與凍結副本，缺一不可，否則引用無法成立。

本批的 run 是「最小權威列承載」：`SEARCH` 與 `FIT` 的 root run 依 #3 的自由設定建立為 `RuntimeRun`，狀態停在 `QUEUED`，不派 worker、不建 attempt、不建 InputSnapshot、不建帳本列；`catalog/tasks.py` 既有 relay 只掃 `INGEST` 與 `ProfileBinding`，故這些列不會被任何 relay 撿走。這是刻意的 Fail-Closed：本批不宣稱 SEARCH／FIT run 已執行，也不宣稱候選來自排程器。

AX-47 的凍結不變條件是本批的驗收核心：`FrozenCandidate.fit_run_id` 必須屬 `Candidate.fit_run_ids`，並與該 FitRun 引用相同 equation／data／observation split／representation；`parameters` 必須是該 FitRun 的完整參數副本；`dsl_identity_hash` 與 EquationVersion 的 `identity_hash` 相同。

離線順序沿用 #3 的決定性 tie-break（development MAE、AST 複雜度、成本形狀、`identity_hash`）；本批把名次持久化為 `development_rank`（1 起算），名次同值時以 `identity_hash` 定序，並以 `Candidate` 唯一鍵完成同結構去重。

## 最小不可變 recipe

`ObservationSplit` 以最小 recipe 落庫，只保存 AX-47 所列的必要欄位：`kind`、三區 row IDs、`gap_rows`／`lookback_rows`／`horizon_rows`、`seed`、時間／群組欄、`group_assignment_digest`、`splitter_version`、`policy_version`、`sealed_final_test`、`sealed_test_id`（本批為 null）、benchmark 引用（本批為 null）、`row_ids_hash`。舊的 `(dataset_version_id, tenant)` 複合鍵一併補上。`ObservationSplit` 不可改；同 `row_ids_hash` 在同一 dataset version 下只留一列。

`RepresentationSpec` 以 identity recipe 落庫：M1 不做降維，因此 `input_dimension`／`output_dimension`／`max_output_dimension` 相等，`inverse_kind=EXACT`、`information_loss=false`、`selection_data_role=DEVELOPMENT`，四個必填 Artifact 引用（config、forward map、row dependencies、unit domain）與可 null 的 inverse map 都指向同一組最小 recipe Artifact。`fit_rows_hash` 必須等於所選 FitRun 的 `fit_rows_hash`，這與 `freeze_recipe_decision` 的四欄一致性要求逐條對齊。

## 凍結決策與零候選診斷

凍結與比較採 `contract_scenarios` 的 `freeze_decision` 為權威裁決，逐條實作且回傳同一組穩定代碼：`FIT_REFERENCE_MISMATCH`、`EQUATION_MISMATCH`、`BINDING_MISMATCH`、`PARAMETER_NOT_CANONICAL`、`BINDING_HASH_MISMATCH`、`REPRESENTATION_MISMATCH`（由 `freeze_recipe_decision` 產生）、`RANK_MISMATCH`、`SNAPSHOT_MISMATCH`。`SNAPSHOT_MISMATCH` 屬 `FrozenSubmission` 的 `snapshot_hash` 檢查，本批不建立該物件，故分支保留而未啟用。

`parameter_binding_hash` 以名稱排序、十進位去冗餘零後的 JSON 算 SHA-256；`canonical_decimal` 逐字沿用 conformance 規則（去尾零、`-0` 折成 `0`、拒絕指數記法），並以範例 `{"a":"2","b":"1"}` 的 `f7a837dc…` 對照驗證。

零候選沿用 `empty_search_decision`：`proposed_count` 為零時不建立任何 Candidate，回報 `SUCCEEDED:INSUFFICIENT_EVIDENCE:NO_VALID_CANDIDATE`；基礎設施失敗回 `FAILED`；預算不足回 `BUDGET_EXHAUSTED`。因為本批 run 未派送，這個結果只落在服務層回報並帶 `product_status=NOT_RUN`，不寫進 run 的 `stop_reason`，避免以不存在的事件冒充已完成的搜尋。

## 儲存不變條件與驗證

0019 建五表並固定唯一鍵與索引：`Candidate` 以 `(search_run_id, equation_version_id)` 唯一、`development_rank` 建索引；`FitRun` 以 `run_id` 唯一；`FrozenCandidate` 以 `(candidate_id, fit_run_id)` 唯一；`ObservationSplit` 以 `(dataset_version_id, row_ids_hash)` 唯一；五表皆補 `(id, tenant)` 唯一鍵供複合外鍵引用。0020 補原生 guard：寫入時 `document` 的 `kind`、`id`、`tenant_id` 與資料列同步、外鍵欄位與 `document` 一致，UPDATE 與 DELETE 一律拒絕；同時補原生複合外鍵到 `(equation_version_id, tenant)`、`(dataset_version_id, tenant)`、`(observation_split_id, tenant)`、`(representation_artifact_id, tenant)` 與 runtime 的 `(run_id, tenant)`，可延遲至交易結束（`DEFERRABLE INITIALLY DEFERRED`），與既有 0016 慣例一致。runtime 0006 擴充 run guard 允許 `SEARCH`／`FIT`，其餘身分與不可變約束不變。

測試涵蓋：真 PostgreSQL 上的唯一鍵與複合外鍵拒絕（含跨租戶引用）、`development_rank` 決定性與同結構去重、`parameter_binding_hash` 對照 conformance 範例、`freeze_decision` 六種拒絕碼逐條觸發、凍結後參數／排名／來源不可改、零候選不建列且診斷正確、`final_test` 不出現在本批任何輸入介面、`SEARCH`／`FIT` run 不被既有 relay 派送。

## 後續切片：凍結提交與最終評估槽位（2026-10-23 補）

上節的排除項有兩段已落地，本節補記其設計，原節保留為當時批次的範圍紀錄。

**凍結提交（catalog 0021／0022）**：`FrozenSubmission` 以 `snapshot_payload` 的 canonical SHA-256 為 `snapshot_hash`，payload 取 `{research_version_id, sealed_test_id, metric_version, evaluation_policy_hash, verification_plan_artifact_id, verification_plan_hash, frozen_candidates}`，其中 `frozen_candidates` 依 `(development_rank, id)` 排序後放整份凍結副本，故同排序同內容重送必得同一 `snapshot_hash` 並讀回原列，不重建身分。`evaluation_policy_hash` 由服務層以版本內 `evaluation_policy` 重算並與版本欄位比對（不符即 `EVALUATION_POLICY_MISMATCH`），`verification_plan_hash` 取驗證計畫內容的 canonical SHA-256；`SealedTest` 必須已登記且可用，否則 `SEALED_TEST_NOT_REGISTERED`。讀取一律經 `authorized_submission` 重新驗租戶與研究 owner 後才回，知道 UUID 不放行。

**最終評估槽位（runtime 0007／0008）**：`FinalEvaluationSlot` 以 `unique(tenant_id, submission_id, frozen_candidate_id, metric_version)` 為業務鍵，同提交／候選／metric 只允許一個槽位與一個評估 run；派送端以 `insert-on-conflict` 取得槽位並讀回既有 `run_id`，重複派送不新建評估 run。槽位建立時必為 `PENDING` 且 `validation_run_id` 為 null，結算單向前進一次（`PENDING → COMPLETED|FAILED`），`COMPLETED` 必須帶 uuid 的 `validation_run_id` 且由 `allOf` 條件與 CheckConstraint 雙重強制；`id`／`tenant_id`／`submission_id`／`frozen_candidate_id`／`metric_version`／`run_id`／`created_at` 不可變，UPDATE 只允許結果引用前進一次，DELETE 一律拒絕。槽位不保存最終結果本身，也不對外曝光。鎖順序依 AX-43：`root → 既有 ancestor／run（深度序）→ SealedTest → ExposureLedger（token_kind／token 排序）→ FinalEvaluationSlot → ResearchBudgetAccount → root BudgetAccount`。

## 後續切片：最終評估固定輸入的派送（2026-10-23 補）

槽位取得後，最終評估的 root 不再走 `catalog/search_run.create`，而由 `catalog/final_manifest.documents()` 產生固定輸入，再經 `runtime.control.enqueue` 與快照、事件同交易落庫。

`documents()` 以凍結提交與凍結候選為權威，吐出四份文件：`TaskInput`（`type=VALIDATE`、`payload.split_role=FINAL_TEST`，帶 `fit_run_id`／`observation_split_id`／`frozen_candidate_id`／`submission_id`／`evaluation_policy_hash`／`verification_plan_artifact_id`／`verification_plan_hash`）、`ExecutionManifest`（`environment_digest`、`input_hash`、`semantic_profile_hash`、`seed`、單一 `isolated-final-evaluator` 插件、`retry_policy.max_attempts=1`）、`BudgetAccount` 與 `RunRecord`（`is_root=true`、`control_only=false`、起始 `dispatch_stage=FINAL_ONLY`）。任一凍結引用不符（候選不在 `frozen_candidate_ids`）回 `FIT_REFERENCE_MISMATCH`，政策雜湊不符回 `EVALUATION_POLICY_MISMATCH`。

固定預留需求為 `cpu_seconds=60`、`gpu_seconds=0`、`tokens=0`、`candidate_limit=0`、`wall_seconds=300`、`memory_bytes=2 GiB`。`limit_for` 以研究設定的限額與帳本剩餘雙重比對：設定限額不足回 `RUN_BUDGET_EXHAUSTED`，剩餘不足回 `RESEARCH_BUDGET_EXHAUSTED`，不以較小的假預留超賣容量。

`runtime/control.py` 的 `_initial` 依型別裁決起始 `dispatch_stage`：`VALIDATE` 只以 `FINAL_ONLY` 派送，其餘 root 一律自 `SEARCH_OPEN` 開始，呼叫端不得自選。`runtime/records.py` 的 `validate_bindings` 新增 `final_bindings`，交叉核對 `dispatch_stage=FINAL_ONLY`、`split_role=FINAL_TEST`、`TaskInput.observation_split_id` 與記錄一致、`retry_policy.max_attempts=1` 四項，不符即拋 `FINAL TEST binding mismatch`，避免探索階段的 manifest 冒充最終評估；`producer_for` 對 `VALIDATE` 給 `t07-validate-v1`，不誤標為 INGEST。`catalog/search_run.py` 的 `KINDS` 收斂為 `SEARCH`／`FIT`。

`enqueue` 在 `created` 時以同一交易建立 `InputSnapshot`（`content_hash = identity_hash([task, execution, budget])`）並 `emit("RunQueued")`；root 入庫後仍無 relay／worker 撿取（既有兩個 relay 只掃 `INGEST` 與 `ProfileBinding`），故不宣稱 `final_test` 已執行。原節當時仍未落地的 `settle` 於 `COMPLETED` 同交易寫最終結果 outbox 與 `ValidationRun` 物件，已於下節「最終結果的同一權威提交」補記；仍未落地者為隔離 Evaluator 的 final_test 執行、曝光帳本 consume、分母與拒答理由、工作台整合。

## 後續切片：最終結果的同一權威提交（2026-10-23 補）

`settle` 自 `PENDING` 單向結算，`COMPLETED` 必須帶完整的最終結果文件，並與槽位、凍結輸入在同一交易落庫。

`catalog/final_evaluation.py` 的 `_verified()` 先以 `runtime-v2.schema.json` 的 `ValidationRun` 契約驗證結果文件（不符回 `INVALID_SCHEMA` 422），再比對 `evaluation_policy_hash` 與凍結提交、`TaskInput.payload` 皆相符（不符回 `EVALUATION_POLICY_MISMATCH` 409），最後逐欄核對 `tenant_id`／`run_id`／`split_role=FINAL_TEST`／`metric_version`／`submission_id`／`frozen_candidate_id`／`fit_run_id`／`observation_split_id`／`verification_plan_artifact_id`／`verification_plan_hash` 與槽位及 TaskInput 一致，任一不符即拒絕落庫。`_record()` 只以核對過的欄位建立不可變 `ValidationRun` 列，結果本身只存在 `document`，故換 UUID 或換一份政策雜湊都不能讓同一份最終評估重複生效。

同一權威提交的順序為：`lock_run` → 結果列 → `register_validation` 證據包（`validation_ids` 只引用該結果、`proof_artifact_ids` 為空）→ `ValidationFinished` outbox（payload 帶 `validation_run_id`／`evidence_bundle_id`／`outcome_status`）→ `save_run` → 槽位更新結果引用 → 提交聚合狀態 `_advance`。`FAILED` 必為 null 且不以新 run 重啟已終止根。`event-v2.schema.json` 的 RUN 流本已允許 `ValidationFinished`，本批不新增事件型別。

`runtime` 0010 建 `ValidationRun` 表並固定五項約束：開發評估的 `unique(tenant_id, run_id, observation_split_id, split_role, metric_version)`、最終評估的 `partial unique(tenant_id, submission_id, frozen_candidate_id, metric_version)`、`split_role` 狀態域、`metric_version` 版本域與「`FINAL_TEST` 必帶非 null 提交／候選引用、其餘必為 null」的互斥；0011 補原生 guard：同租戶複合外鍵（可延遲至交易結束）、`document` 與資料列欄位同步、`valid_count + failed_count = selected_count` 的分母一致，以及 UPDATE／DELETE 一律拒絕。`foundation/health.py` 的必要 migration 集合已加入這兩支。

仍未落地：隔離 Evaluator 的 final_test 執行與 `Vault.read_final` 的授權讀取（原節所列的 `SealedTest` 原子預留與曝光帳本 consume 已於下節「曝光預留與消耗接線」補記）、分母與拒答理由的產出端、工作台整合。

## 後續切片：曝光預留與消耗接線（2026-10-23 補）

`catalog/sealing.py` 對封存域的接入補上三個薄包裝：`reserve()`、`consume()`、`retire()`。三者都以凍結提交的 `sealed_test_id` 為封存身分、`tenant_id` 為租戶，並以提交自身與其 `snapshot_hash` 呼叫 `Vault.transition`；`RETIRE` 例外地不帶提交身分，因為保守退役只需關閉曝光，不應覆寫既有綁定。`Vault` 的 `SealRejected` 在此轉成 `ApiError`：`NOT_FOUND` 保留 404，其餘一律 409——遮罩失敗不可回 503，否則 `catalog/http.py` 的 `error_response` 會把它標成可重試而誤導呼叫端。

**預留時機裁定**：AX-43 明言「slot 建立、run／manifest、預留與 outbox 在同一 root 鎖與觀測帳本鎖順序內完成」，AX-05 的故障恢復表則把 `RESERVED` 放在「綁定唯一 `submission_id`」的同一列。兩者都指向「決定要把哪個提交送上最終測試」的那一刻，而非「真的讀到 final labels」的那一刻；後者是 `CONSUMED`。故 `acquire()` 在 `_validate_root()` 之後、`FinalEvaluationSlot.objects.create()` 之前呼叫 `reserve()`，使 root、輸入快照、曝光預留與槽位共用同一 savepoint：輸掉競態的一方整批回滾，Vault 端的預留因綁定同一提交／快照而冪等重播，不會留下孤兒 run 或半套曝光。

**消耗與退役**：`settle()` 前進曝光的時機是「槽位已鎖定、確認為 `PENDING`、且結果身分已逐欄核對通過」之後：`COMPLETED` 先 `consume()` 再落結果列，`FAILED` 走 `retire()`（保守退役，不回 `AVAILABLE`）。核對排在消耗之前，是為了不讓一份不合格的結果燒掉不可回復的封存資格；任何被拒的結算因此完全不改動帳本。`CONSUMED` 之後 `Vault.read_final` 才第一次放行且授權副作用只在讀 blob 前觸發。隔離 Evaluator 上線後消耗由讀取端先行提交，`settle()` 的呼叫即成為純 replay，此排列屆時不影響語意。隔離 Evaluator 的實際執行仍不在本切片，故本節只保證帳本狀態正確，不宣稱 final labels 已被讀取。

**測試接線**：`sealed_authority()` 由 `test_profile.py` 收斂到 `catalog/tests/test_sealing.py` 成為全 catalog 共用夾具（以同一 authority 檔的 in-process journal 取代私有 RPC，封存 child 仍是真實子程序）；`test_final_evaluation.py` 的 `register_seal()` 改為真實 `Vault.register`，逐案核對 `RESERVED`／`CONSUMED`／`RETIRED` 的可觀察後果（未消耗前 `read_final` 回 `INVALID_TRANSITION` 且 `authorize` 不被呼叫、退役後不可再 `RESERVE`、別的提交或快照回 `TEST_ALREADY_RESERVED`），不再以假登記冒充已封存。

仍未落地：隔離 Evaluator 的 final_test 執行與 `read_final` 授權讀取（已於下節「隔離 Evaluator 的 final_test 執行」補記）、分母與拒答理由的完整語意、工作台整合。

## 後續切片：隔離 Evaluator 的 final_test 執行（2026-10-24 補）

`catalog/final_evaluator.py::validate_tick` 收束前兩節所列的「隔離 Evaluator 的 final_test 執行」與「`Vault.read_final` 的授權讀取」。

**曝光順序**：`consume(submission)` 先行提交，再 `authority().read_final(tenant, identity, submission, snapshot, authorize)` 讀取 final labels。`read_final` 只認 `CONSUMED` 狀態且要求 `submission_id` 相符，`authorize` 回呼內重驗租約與截止時間（`check_submission`），故授權副作用只在讀 blob 前觸發；`settle()` 內的同名 `consume` 因此是純 replay，與前節「消耗由讀取端先行提交，`settle()` 即成為純 replay」的裁定一致。

**曝光保守關閉**：`read_final` 失敗、payload 不可解析或評分失敗，一律走失敗結算並以 `retire()` 退役曝光，不回 `AVAILABLE`；不可復活由 `Vault` 端保證（已退役後 `RESERVE` 回 `TEST_ALREADY_CONSUMED`）。

**評分**：final labels 以 canonical rows 傳遞，每列必須恰有一個輸入與一個目標，非此形狀一律收斂成 `INVALID_SCHEMA` 422，不讓 JSON 解碼例外逃出 worker。凍結候選的參數取自 `FrozenCandidate` 的正規副本、DSL 取自 `EquationVersion`，經 `compile_dsl` 後交 `mathematics.metrics.score`；結果的 `selected_count`／`valid_count`／`failed_count`／`coverage`／`mae`／`rmse` 全部來自公開評分函式，評估器不另行計算。

**結帳**：`runtime.completion.finish` 是唯一終態入口；evaluator 不呼叫 `budget.report_usage`／`release_unstarted`／`remaining`（`VALIDATE` root 依設計沒有帳本列），`usage` 只作實際用量回報。結算（`final_evaluation.settle`）在 `finish` 的 `commit()`／`failure()` 回呼**內**執行，使槽位與 root 的終態同一次裁決；資源超支時 `finish` 改走 failure 回呼，槽位與 root 終態因此永遠一致。

**事件游標**：回呼可能已就同一 root 再寫事件（`ValidationFinished`），故 `finish` 於回呼返回後以同一鎖入口補回最新 `current_event_cursor` 再寫終態事件，避免終態事件與回呼事件撞號；回呼在記憶體的其他變動（如 INGEST 失敗時附加的 `diagnostic_artifact_ids`）仍以原物件保存後一併落庫。

**判定準則**：`outcome_status` 先以 `baseline=FIT_MEAN` 的 fit 均值（取自 `ResearchState.quality_id` 指向的 `QualityReport.fit_summary.target_mean`）建立 baseline；來源缺失、`error_model=UNSPECIFIED`、`comparison_method=NONE`，或無可評分列（`mae` 為 null／`valid=0`／`valid<selected`）皆回 `INSUFFICIENT_EVIDENCE`。本切片先落地這條最小可裁決路徑；paired bootstrap、practical margin 與完整的 `AMBIGUOUS` 語意於下節「比較語意與實務邊界」補記。

**派送與服務邊界**：`catalog/tasks.py` 新增 `relay_validate()` 與 `catalog.validate_tick` 任務，`dispatch_probes` 迴圈一併掃描；`settings.VALIDATE_ENABLED`（`AXIOM_VALIDATE_ENABLED`）未啟用時 relay 只做恢復而不派送。`compose.yaml` 另設專用 `evaluator` 服務（`--queues=validate`、`--concurrency=1`、`--max-tasks-per-child=1`、sealed-data／sealed-keys／journal socket 與唯讀 object 資料卷），使隔離評分只吃得到封存通道與固定輸入。

**結果身分**：A1 不為 `ValidationRun` 建 `Artifact`（`register` 的 `access_class='PROJECT'` 白名單不含 `ValidationRun`，且 `Artifact.dataset` 非 nullable），故 `artifact_uri` 以 `private://evaluator/final-report/{identity}` 合成、`sha256` 為結果自身可重算的雜湊；因 canonical 身分不收浮點，摘要前把數值投影成正規十進位字串。

仍未落地：分母與拒答理由的完整語意（paired bootstrap、practical margin、`AMBIGUOUS`）已於下節「比較語意與實務邊界」補記；仍未落地者為槽位對外端點與工作台整合（#6）。

## 後續切片：比較語意與實務邊界（2026-10-24 補）

上節的「判定準則」把 `outcome_status` 收在「候選 MAE vs baseline」的大小比較；本節改以配對 bootstrap 的 95% 區間與實務邊界的關係裁決，落地 AX-28 的完整語意。

**純計算核心**：比較語意集中在 `mathematics/comparison.py`（`scale`／`bound`／`baseline_losses`／`interval`／`classify`），逐列配對損失則由 `mathematics/metrics.py::residuals` 提供（回傳每個 matched 列的 `(target, loss)`，`score` 重用同一函式，故計數與 `mae`／`rmse` 與配對來源一致）。

**決定性重抽樣**：`interval()` 對 matched 的逐列損失差（`candidate - baseline`）做 IID 有放回重抽樣 `bootstrap_replicates`（政策固定 2000）次，軌跡平均值取 `[1/40, 39/40]` 百分位為 95% 區間。索引由 `identity_hash([RESAMPLING, seed, replicate, draw]) % count` 導出（`RESAMPLING="axiom-paired-bootstrap-sha256-v1"`、`seed` 取自政策 `bootstrap_seed`），不依賴直譯器 PRNG，故跨環境與跨 Python 版本可重現；`quantile` 沿用 `mathematics/metrics.py` 既有實作。配對以共用索引對齊兩端，混合差的正負兩端不會被互相平均掉。

**practical margin**：尺度取 `max(IQR(y_fit), measurement_resolution)`——`IQR` 為 `QualityReport.fit_summary.target_iqr`、解析度為 `SemanticProfile.measurement_resolution`；兩者皆 0 時只認預先註冊的正 `practical_scale_override`，否則沒有可比較的帶寬（`margin` 為 null ⇒ 拒答）。`margin = scale × practical_margin_ratio`（ratio 於建立版本時已限定在 `(0,1]`，預設 0.01）。

**四態判定**：`classify()` 依區間與 margin 的位置產出 `Outcome`：`upper < -margin → SUPPORTED`、`lower > +margin → FALSIFIED`、`[-margin, +margin] ⊇ [lower, upper] → AMBIGUOUS`、其餘（區間跨越實務邊界）→ `INSUFFICIENT_EVIDENCE`。順序先判兩側極端、再判帶內等效，殘餘者一律 `INSUFFICIENT_EVIDENCE`，故四態互斥且窮盡。

**拒答閘**：`final_evaluator._outcome` 先檢查 `error_model==UNSPECIFIED` 或 `comparison_method != IID_PAIRED_BOOTSTRAP` 即回 `INSUFFICIENT_EVIDENCE`（`comparison_method=NONE` 因此只輸出描述性指標並拒答，對齊 AX-28）；再檢查 `mae` 為 null／`valid==0`／`valid<selected`／baseline 為 null／margin 為 null 亦拒答；通過才進重抽樣。`interval` 的呼叫以 lambda 延遲，故所有拒答分支都不觸發評分。

**接線**：`final_evaluator._evaluate` 以 `_fit_summary` 取 fit 摘要、`_decimal` 解析十進位、`_baseline` 決定 baseline、`_margin` 算外邊界、`_outcome` 產出狀態；`ResearchVersion` 的 `evaluation_policy` 為唯一政策來源，評估端不自選比較方法。

**測試**：`mathematics/test_comparison.py` 以純函式窮舉 `scale`／`bound`／`baseline_losses`／`interval`／`classify`（含決定性、seed 敏感與區間退化）；`catalog/tests/test_final_evaluator.py` 新增 FALSIFIED／AMBIGUOUS／`comparison_method=NONE` 拒答三項端到端。因私有符號（`_outcome`）跨模組引用會被 pyright strict 拒絕，拒答分支一律經 `validate_tick` 端到端覆蓋，不直接 import。

仍未落地：槽位對外端點與工作台整合（#6）。
